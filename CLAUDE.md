# CLAUDE.md — paragliding forecast

## What this is
A daily forecast of how good tomorrow (and the next 5 days) is for **Mystic launch, Bright, Victoria**: an XC % and an acro %, shown on a phone-friendly dashboard.
Built so more sites can be added later: Organyà (restitution), Flowerdale, Dandenongs, Manilla. A site = `sites/<id>.yaml` (location, timezone, flying window, BOM stations) + `sites/<id>/rules.yaml` (limits) + `sites/<id>/notes.md`.
Owner: Fabian. Plain, short explanations; he is technical but not a data scientist.

## Names
- **"The rules"** = Fabian's and his brother's flying limits in `sites/bright/rules.yaml` (each rule scores 0–100%; a day's score is its weakest rule).
- **Creo** = the planned machine-learning model. Not built yet.
- **Creo (beta)** = the panel on the dashboard that replaced the AI second opinion on 2026-11-27: a rating word from the typical outcome of past days with a similar Creo estimate (median actual best flight: Poor under 5 km, Fair 5-20, Good 20-50, Great 50 or more, Great being the top word; the estimate cut points and day counts are in `sites/bright/creo_model.json`) and up to four short template lines (no AI): how often similar past days went XC (best flight 20 km or more; curve stored in `creo_model.json`), Best (window from the XC bars, climbs to the day's thermal top at its rate, plus a helper only if it isn't thermals), Watch (the biggest drag with its value; wind aloft is described at the thermal top), (on a Poor day Watch comes before Best) and a last line only when Creo and the rules clearly disagree. Factors come from LightGBM per-feature contributions added up into one net effect each. Never shows km. On a no-go day it leads with the rules' deal-breaker. It never changes the scores.
- **AI second opinion** = retired from the daily job (no API key or cost any more); `src/pgforecast/ai_opinion.py` and its tests stay in the repo, unused.

## How it runs
- **Model weighting**: the job blends the models per variable with `sites/bright/model_weights.json` (ACCESS-G dropped, GFS out of gusts) and then scores the blend. **Currently `model_weighting: equal` (the old method stays live until the one-month review, ~2026-12-26)**; switch with the GitHub variable `MODEL_WEIGHTING` (`weighted` or `equal`, Settings > Variables) or `model_weighting` in `sites/bright.yaml`. Both blends and the old average are logged in `predictions/weighting_log.csv`.
- **GitHub Actions** (`.github/workflows/daily.yml`, 07:45 and 19:45 Melbourne time): collect BOM observations, update bias corrections, valley-wind calibration check, wait for the newest ECMWF/GFS/ICON runs, fetch forecasts, score, rebuild the dashboard, commit the results back to `main` as "Daily update".
- **Creo (beta)**: each daily run predicts the best distance for every forecast day with `sites/bright/creo_model.txt`, appends it to `predictions/creo_log.csv` next to the rules' XC % (the shadow log that `creo_review.py` scores) and puts the rating word and the why on the dashboard (no km). It never changes a score, and any failure there is skipped (the panel is left out) (the job installs LightGBM in its own non-blocking step). Retrain with `scripts/creo_train.py` (writes the model and `creo_model.json`, which records each version's training cut-off), commit, and the job picks it up.
- **Laptop (by hand)**: everything that isn't the daily job runs here today: downloaders (`fetch_barra2.py`), importers (`import_xcontest.py`, and `import_chats.py` using Haiku via the API, key from `ANTHROPIC_API_KEY`, cost-capped). Weekly jobs are **planned, not built**.
- **Home desktop (later)**: heavy downloads and local AI (e.g. a local model for the chat importer). Not in use yet.
- **Where data lives**: the daily job commits only `observations/ forecast_archive/ predictions/ model_runs/ corrections/ docs/`. Everything else is local and git-ignored: `data/` (SQLite: forecasts, chat labels, XContest flights, BARRA-C2 in `data/barra2/`, the hashing salt `data/chat_salt`), `xcontest_pages/`, `chat_exports/`, `igc_files/<pilot>/` (pilots' IGC/GPX tracks, shared with permission; folder = pilot identity).

## Adding a site (any country)
1. `sites/<id>.yaml`: copy `bright.yaml` — location points, timezone, flying window. Put BOM stations in only for Australian sites.
2. `sites/<id>/rules.yaml` (limits) and `notes.md`.
3. `sites/launches.yaml`: one entry per launch, each with `site: <id>`, its own `id`, region, country (ISO), timezone, lat/lon and `radius_m`. Several launches can share one site. Never rename a launch `id` once flights are imported.
4. Re-run `python scripts/import_igc.py igc_files`: it re-tags every stored flight to the current launch list, so new or moved launches apply to flights already imported.
5. Weather for past days: **BARRA-C2 is Australia-only** (BOM reanalysis, `scripts/fetch_barra2.py`). Overseas sites (Organyà, Bir...) need **ERA5** (global, ~25 km, hourly, Copernicus CDS), or **CERRA** for Europe (~5.5 km, covers 1984 to about mid-2021; check the CDS page for its end date). Not built yet. Timestamps are UTC in all of them; the site's own timezone is only for display.
6. Track timezones need no setup: they come from each flight's coordinates (`tzlookup.py`; oddities in `sites/timezones.yaml`).

## Run the main scripts (from the project root, `.venv` active)
- `python scripts/daily_forecast.py bright` — fetch, score, rebuild `docs/` (normally run by GitHub).
- `python scripts/fetch_forecasts.py bright [--until YYYY-MM-DD]` — fetch/archive forecasts.
- `python scripts/collect_bom.py bright` — append BOM station observations (the GitHub job writes `observations/`; on the laptop it writes `data/local_out/observations/`).
- `python scripts/update_corrections.py bright` — bias corrections from forecasts vs observations.
- `python scripts/calibrate_valley_wind.py bright` — valley-wind check (reports only).
- `python scripts/fetch_barra2.py bright` — BARRA-C2 reanalysis boxes into `data/barra2/` (resumable).
- `python scripts/import_chats.py chat.txt --default-site bright` — chat labels (`--backend anthropic` for Haiku; `--dry-run` to count).
- `python scripts/import_xcontest.py --summary` — import saved XContest pages; warns about incomplete months.
- `python scripts/import_igc.py igc_files` — import `.igc` and `.gpx` tracks from `igc_files/<pilot>/` offline into `data/igc_flights.sqlite` (flights, thermal circles, launch site by coordinates, sample-rate flag). Folder name = pilot (hashed). Each flight's local time uses the timezone of its launch coordinates (`tzlookup.py` using the `timezonefinder` package, laptop only: `pip install -r requirements-igc.txt`; hand overrides in `sites/timezones.yaml`). Re-run safe; prints a summary and lists skipped files.
- `python scripts/thermal_zones.py --split ring` — Emily vs Marcus thermals at Mystic vs BARRA-C2 weather (read-only analysis, pilot1 only by default; writes `data/thermal_zones/`).
- `python scripts/forecast_error.py bright` then `python scripts/forecast_error_report.py` — forecast error vs BARRA-C2 (11:00–16:00 local; read-only). Writes `data/forecast_error/` (`error_summary.csv`, `pairs.sqlite`, `priors.json`, `priors_slim.json`, `report.md`; never touches the committed `sites/bright/priors.json`). Dashboard unchanged.
- `python scripts/barra_terrain.py bright` — BARRA terrain height vs Open-Meteo elevation per point (`data/forecast_error/elevations.json`; needed by `forecast_error.py`).
- `python scripts/fetch_bom_dwo.py 202103` then `python scripts/forecast_error_stations.py` — BOM Daily Weather Observations (Hotham, Falls Creek, Wangaratta; ~13 months) and the forecast-vs-station check.
- `python scripts/model_weights.py [--publish]` — per-variable model weights (`data/forecast_error/model_weights.json`); `--publish` writes the committed `sites/bright/model_weights.json` that the daily job reads (approved 2026-11-26). `sites/bright/priors.json` = BARRA-based corrections kept for reference only: **do not apply** (they made real error worse; `scripts/validate_corrections.py`).
- `python scripts/weighting_review.py bright` — equal vs weighted blends scored against the BOM stations (runs in the daily job; opens one GitHub issue after 30 days). `python scripts/check_observations.py bright` — gaps in the saved BOM observations (also in the job). `python scripts/validate_corrections.py` — tests bias corrections against real station readings.
- `python scripts/scoreboard.py` — how well the current XC rules predicted real flying at Mystic (2022 on, complete XContest months only, the same days as Creo's tests): XC % from the archived forecasts (A) and from BARRA-C2 (B) vs flown / best distance (XContest + IGC, no tandems, unknown days skipped). Bands, seasons, weekends/holidays, with/without Bright Open, biggest misses. Writes `report.md` + `days.csv` into `--out` (default `data/scoreboard/latest/`, so it never overwrites the saved reports in `data/scoreboard/`; local). Ties for "held back by" go to the first name alphabetically. `--lead d1` scores the day-ahead forecast instead. Holidays and Bright Open weeks are in `sites/bright/calendar.yaml` (check them); `days.csv` marks comp days: `comp`, `flyable` (kept), `count_weight` 0 and `distance_weight` 0.5, which training must use. Acro: not scoreable until chat labels carry acro days. Read-only; reruns in seconds.
- `python scripts/rule_tests.py [--variants baseline,west,west_valley]` — tests possible XC rule changes against real flying, leave-one-year-out, without touching the live rules (variants: baseline, west, west_valley, rain, west+rain; see its docstring). Needs `days.csv` from the scoreboard (in `data/scoreboard/latest/`). Writes `rule_tests.md` there. A change is kept only if Fabian approves.
- `python scripts/creo_test.py` — first Creo test, report only (LightGBM, `pip install -r requirements-creo.txt`): predicts a day's best distance (log) from forecast-side weather, the rules' scores and day of year, leave-one-year-out, compared with the rules' XC % by rank correlation. Free-day flag set to 1 when predicting; a rules no-go (XC % 0) forces 0; comp-day distance weights used. Writes `data/creo/report.md`. Not in the daily job.
- `python scripts/creo_train.py` — trains Creo on every usable day and saves `sites/bright/creo_model.txt` (+ `creo_model.json`) for the daily job's shadow mode. `python scripts/creo_review.py` — scores the logged Creo and rules predictions in `predictions/creo_log.csv` (pull first) against the imported flights with the scoreboard method, per forecast lead (lead 0 rows are ignored: they can be made after the flying window), days the model trained on left out. Writes `data/creo/review.md`.
- `python scripts/fetch_single_runs.py --workers 3` — Open-Meteo Single Runs API: the 00 UTC run of each day (GFS, ECMWF 0.25, ICON; all variables incl. 850/700 hPa winds) into `data/single_runs/` (local). The API keeps runs only from about April 2026 and answers about one request per 30 s, so ~240 runs take ~2 hours; resumable, stops on any error. `python scripts/creo_walkforward.py` — walk-forward test of Creo: each week trains on the days before it, predicts from forecasts issued 1 and 2 days ahead (Part A: Single Runs, full variables, April 2026 on; Part B: Previous Runs, no 850/700 hPa winds, cloud cover or boundary-layer height, from 2025-12-01), rules scored on the same forecasts. Writes `data/creo/walkforward.md`.
- `python scripts/fetch_ffwx.py` — Mystic weather station (FreeFlightWx) CSV -> 10-minute averages in `data/ffwx/mystic.csv` (local). One request per run; it picks the window itself: nothing saved -> 720 h, newest saved row under 24 h old -> 24 h, else the smallest window covering the gap (max 720 h; warns if readings are lost). The station only looks back N hours from now (dates are ignored). Only the last ~24 h comes at full 11 s resolution; longer windows are thinned (~1 reading per 3-4 min), so the `resolution` column marks each row `full` or `thinned`: **training must ignore wind max/min (gusts) of thinned rows**. A later full download of the same 10 minutes replaces a thinned row. Contact for the user-agent comes from `FFWX_CONTACT` in `~/.profile`. Runs daily from a systemd user timer on the laptop (`~/.config/systemd/user/ffwx.timer` 12:00, `Persistent=true` so missed runs happen on wake; `ffwx.service` runs it through `bash -lc`; log: `journalctl --user -u ffwx.service`). User timers only run while Fabian is logged in (linger is off). Not used by the forecast or corrections yet.
- `python scripts/fetch_era5.py` — ERA5 raw collector (CDS key in `~/.cdsapirc`, never printed; `pip install -r requirements-era5.txt`; ERA5 licence accepted on the CDS site). Area N-20 W110 S-50 E160, 0.25 deg, every 3 h UTC, 2008-01 to ~6 days ago. Single levels (msl, tcwv) and pressure levels (z, u, v, t at 500/700/850 hPa: all 12 fields, because CDS can't pick single pairs). One file per dataset per month in `data/raw/era5/` (`era5_single_YYYY_MM.nc`, `era5_pressure_YYYY_MM.nc`), local, git-ignored. One request at a time (CDS rejects a second queued request, even for the other dataset; tested 2026-11-28); order: all single months (~90 s each), then pressure (long queue), up to 3 full months of one year per pressure request (CDS size limit 60000: 1 month ~18000, 3 months ~52000, 4 would not fit); the download is split by month (values unchanged) and every month file is verified and listed in the manifest as before; a failed batch falls back to single-month requests; CDS job ids in `jobs.json` so a restart re-attaches. Each file is downloaded to `.part`, verified (opens, variables, levels, grid/area, exact time steps, no missing values) and renamed; one retry, then logged and skipped. `manifest.csv` records size, steps, verified, download time and `preliminary_expver5` (ERA5T months; `--refresh-preliminary` re-downloads them when final). The current month is partial and is topped up on a later run. Resumable. Stops if free disk is under twice the estimate. Raw files only: no tables or weather types yet. Runs as the systemd user service `era5.service` (`~/.config/systemd/user/`, restarts on failure, resumes after reboot; user services only run while Fabian is logged in, linger is off). Progress: `data/raw/era5/progress.log` (one line per file with ETA), detail in `fetch.log`; `systemctl --user status era5.service`; `--estimate` prints the estimate only.
- `scripts/commit.sh "message"` — pull --rebase, add code paths only, commit, push.
- Tests: `unittest`, not pytest (pytest is not installed): `PYTHONPATH=src .venv/bin/python -m unittest tests.test_<module>` for each file in `tests/`; `test_fronts` needs `PYTHONPATH=src`.

## Standing rules
- **Git from the laptop**: pull first. Never commit `docs/`, `forecast_archive/`, `predictions/`, `observations/`, `model_runs/`, `corrections/` — the daily job owns them. `scripts/commit.sh` adds only code paths (never `git add -A`) and the pre-commit hook blocks those folders as a backup; use `commit.sh` or add paths explicitly.
- **Never commit** data, databases, credentials/API keys, `chat_exports/`, `xcontest_pages/`, or pilot names.
- **Never fetch anything from XContest.** Only read pages Fabian saved by hand into `xcontest_pages/`.
- **Pilot names are always hashed** (`store.pilot_hash`, salt in `data/chat_salt`); never store or print raw names.
- **Ask first** before anything that costs money (paid APIs, big downloads), deletes data, or changes the live site in a big way.
- Units: **km/h, metres, Victorian local time** (Australia/Melbourne, AEST/AEDT). Heights ASL unless stated.
- **Creo (beta) never changes scores** (it only adds the rating and the why to the dashboard; every run is also logged to `predictions/creo_log.csv` for `scripts/creo_review.py`).
- The rules' **deal-breakers are hard limits**: no model (including Creo) may override them.
- Months listed under `unknown_months` in `sites/bright/calendar.yaml` (2025-09, 2025-10, 2025-11: possible site closure) are left out of the scoreboard and Creo's training completely, flown days included.
- Months where saved XContest flights are more than 2 short of XContest's total are **incomplete** (a month short by 1–2 counts as complete; `xcontest.MONTH_TOLERANCE`); for Creo training every day of an incomplete month is dropped, flown days included (they would make the month look 100% flown); days with no saved flights there are **unknown**, not "nobody flew" (`xc_day_status`). Tandem (class T) is stored but excluded from XC grading (`xc_flight_graded`).
- Every change must update SPEC.md and PLANS.md in the same commit.
- Keep this file, the README-style notes and the tests current when behaviour changes. Log decisions in `DECISIONS.md`; tick `TODO.md`.

## Working style
- Do only what the prompt asks. Don't suggest extra features, improvements or follow-up ideas.
- Do report bugs, wrong results, data problems or risks, briefly.
- TODO.md only holds real actions with a clear result. No ideas or nice-to-haves.
